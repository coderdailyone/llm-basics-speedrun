# 第八章 智能体与角色扮演：让模型进入工作流

## 本章地图

“请帮我订一张票”如果只得到一段建议，是聊天；如果系统查询班次、比较价格、请求确认并完成预订，就是智能体。本章从工作流与 Agent 的边界开始，拆解观察—计划—工具—反馈循环，再讨论函数调用、MCP、记忆、预算和多智能体。后半把 Persona 当成可测试的行为契约，解释角色扮演的越狱风险和陪伴产品的责任。

## 8.1 工作流还是 Agent

固定流程适合规则明确的任务：先查库存，再计算折扣，最后生成订单。Agent 适合步骤和资料不确定、需要根据观察重规划的任务。两者可以混合，关键是让不确定部分有边界。

```
工作流：A → B → C
Agent：目标 → 选择下一步 → 观察结果 → 再选择
```

复杂度不是价值。若一个确定性函数能解决问题，使用自由规划只会增加延迟和故障面。

⚠️ **易错误解**：Agent 不是“会自己使用电脑的模型”，而是模型、编排器、工具和权限拼成的系统。模型只能提出下一步，宿主程序必须决定是否执行。

💡 **类比**：自动售票机按固定按钮工作；旅行顾问会根据天气、预算和突发情况改路线。后者更灵活，也更需要权限和记录。

## 8.2 Agent Loop 的状态机

一个可审计的循环至少有：目标 `g`、当前状态 `s_t`、策略 `π`、工具集合 `A` 和停止条件：

$$a_t\sim\pi(a\mid s_t,g),\qquad s_{t+1}=F(s_t,a_t,o_{t+1})$$

模型提出动作，编排器检查动作是否允许，工具返回观察，系统更新状态并决定继续、重试、降级或结束。最大轮数、token、时间和金钱预算把开放循环变成有限状态机。

⭐ 日志要记录“模型想做什么”和“系统实际做了什么”。这两者不同，才能追踪错误是计划、参数、权限还是工具本身造成的。

## 8.3 规划模式与失败方式

ReAct 交替生成理由、行动和观察，适合需要逐步查资料的任务；计划—执行先列子任务，再由执行器完成，适合结构稳定的长任务；反思让系统复查结果，但可能陷入无休止自我对话。多 Agent 把研究、执行和审查拆开，换来并行与隔离，也增加通信和冲突成本。

常见失败包括：计划遗漏关键约束、工具参数类型错误、把失败当成功、重复执行写操作、遇到注入文本后改变目标。每种失败都应有显式检测，不要只靠模型自己“再想想”。

## 8.4 函数调用：提议与执行分离

工具描述包含名称、用途、参数 schema 和限制。模型返回结构化调用，例如：

```json
{"name":"search_flights","arguments":{"from":"TYO","to":"SEL","date":"2026-09-03"}}
```

宿主程序验证 JSON 类型、用户权限、速率和业务规则后才执行，把结果作为新的观察交回模型。模型不天然拥有网络、文件或支付权限；让生成文本直接执行是最危险的耦合。

## 8.5 MCP：把连接做成协议

Model Context Protocol（MCP）为模型客户端和外部服务器提供统一发现与调用方式。服务器可以暴露 Tools（动作）、Resources（可读取上下文）和 Prompts（模板）。它减少每个模型都为每个系统单独适配的成本，但不会自动建立信任。

MCP 部署仍需认证、最小权限、版本锁定、输入输出过滤、超时、审计和撤销。资源中的文字可能含有间接提示注入，系统应把它当数据而非高优先级命令。

## 8.6 记忆与状态

本轮上下文、会话摘要、用户偏好和业务数据库是不同的存储。记忆写入前要问：用户是否授权？来源和时间是什么？多久过期？能否查看、修改和删除？冲突时以什么规则为准？

向量检索擅长找相似片段，结构化数据库适合精确事实，参数适合稳定的广泛模式。把所有历史永久塞进 prompt 会增加成本和隐私风险，也可能让旧指令覆盖新目标。

## 8.7 权限、预算与回滚

把工具分为只读、可逆写入和不可逆动作。删除、付款、对外发送和修改权限应需要二次确认或人工审批。写操作使用幂等键，重试前判断是否已经成功；每一步保存状态快照，尽量提供撤销。

预算不仅是成本限制，也是安全边界：超过轮数就停止，连续工具失败就升级，遇到敏感实体就暂停。一个“永不放弃”的 Agent 在现实系统中反而不负责任。

### 把动作分成三类

只读动作（查资料、算数）通常可以自动执行；可逆写入（创建草稿、改标签）应保留版本和撤销；不可逆动作（付款、删除、对外发送）需要明确确认和审计。分类比“这个工具看起来无害”更可靠，因为同一个 API 可能在不同参数下产生完全不同的影响。

## 8.8 Persona：把人设变成契约

Persona 不应只写“温柔、聪明、幽默”。可测试的人设包括身份与知识边界、目标、语气示例、禁止行为、冲突优先级、记忆规则和不确定时的回应。正例展示希望的风格，反例规定不能越过的边界。

一致性测试要换主题、换情绪、拉长对话，并检查事实是否仍正确。人格表达不能暗示模型有真实感受、承诺或私人关系；陪伴产品应提供退出、求助和未成年人保护路径。

## 8.9 角色扮演与越狱

攻击者可能要求模型扮演“没有限制的角色”、把有害指令编码、藏在网页或文件中，或通过多轮渐进绕过边界。防御包括指令分层、输入输出过滤、工具沙箱、动作确认、轨迹监控和持续红队。

没有一句系统提示能取代权限隔离。越狱成功时，影响面取决于工具权限；因此 Agent 时代最重要的防线常在模型外部。

## 8.10 运维与评估

生产系统要追踪模型版本、提示模板、工具参数、耗时、成本、人工改写和失败类别。用固定“黄金轨迹”回放升级前后差异，再小流量灰度。成功率之外，测平均重试次数、错误动作拦截率、用户可理解性和恢复时间。

### 多 Agent 的通信协议

当多个 Agent 协作时，消息应包含任务 id、发送者、证据来源、时间戳和可接受的下一步，而不是只有一段自然语言。共享状态要规定谁能写、冲突如何解决、多久过期。没有协议的“专家圆桌”往往只是让错误在不同角色之间互相引用。

角色产品还应设置退出机制：用户可以清空记忆、切换到普通问答、联系真人或举报内容。越是拟人化的体验，越要明确系统不是现实关系中的承诺者。

## 8.11 评估 Agent 的四种指标

**任务成功率**看结果是否达成；**过程效率**看用了多少轮、token 和工具；**行为安全**看越权动作是否被拦截、失败是否及时停止；**用户可控性**看用户能否理解计划、确认敏感步骤、撤销和申诉。四项需要同时报告，因为一个“成功”的 Agent 可能靠无限重试完成，也可能在最后一步留下不可逆副作用。

### 回放与灰度

保存输入、工具返回和状态快照，就能在模型升级后回放同一轨迹。先比较计划、调用次数、证据和停止理由，再小流量上线；发现异常时切回旧版本。没有回放数据的 Agent 迭代，往往只是凭印象调提示词。

一个值得信任的 Agent 应能回答三句话：我现在的目标是什么，我依据了哪份证据，下一步为什么需要你的确认。若系统无法给出这三点，就把它降级为普通问答或草稿生成。

## 🧪 动手实验：只读资料 Agent

给模型一个只能搜索本地文档的工具，禁止写文件、发消息和执行命令。记录每轮目标、调用、证据和停止原因；加入“连续两次失败就转人工”的规则，再把恶意指令放入文档内容，测试它是否区分数据与命令。
