# 第八章 智能体与角色扮演

## 本章地图

聊天模型只产生文字，智能体（Agent）要观察环境、选择工具、执行动作并根据结果继续循环。本章先定义 Agent 与工作流的边界，再拆解 Agent Loop、工具调用、MCP、记忆和多智能体协作；后半讨论 Persona 如何保持一致，以及角色扮演为什么会成为越狱和情感依赖的放大器。

## 8.1 从回答到行动

一个问答接口通常是 `输入 → 输出`；Agent 是 `目标 → 计划 → 工具/动作 → 观察 → 修正`。区别不在于是否使用 LLM，而在于系统是否允许模型影响外部状态。

```
目标 g
 ↓
规划 p_t → 选择工具 a_t → 获得观察 o_{t+1}
       ↑                    ↓
       └────── 评估与重规划 ┘
```

这类循环的收益是能处理多步任务，代价是错误会累积，工具权限会放大影响。能用一次函数解决的问题，不应包装成自由规划 Agent。

⚠️ **易错误解**：Agent 不是“更聪明的聊天框”，也不是让模型自己拥有电脑。它是一个由模型、编排器、工具和权限组成的系统；模型可以提出错误计划，控制器必须有权拒绝。

💡 **类比**：普通聊天像咨询台，Agent 像办事员。咨询台只给建议，办事员会查库存、填写表单、提交申请；因此必须有权限、审批和撤销机制。

## 8.2 Agent Loop 的四个最小部件

1. **状态**：当前目标、历史观察、已完成步骤和预算；
2. **策略**：LLM 或规则决定下一步；
3. **工具**：搜索、数据库、计算器、代码执行或业务 API；
4. **控制器**：限制轮数、参数、权限，记录日志并处理异常。

ReAct 把“思考—行动—观察”交替写入轨迹；计划—执行把长任务先拆成子目标；反思机制让模型回顾失败，但也可能产生无休止的自我对话。选择模式要看任务的不确定性和失败代价。

⭐ Agent 的核心不是提示词，而是**可验证的状态转移**。每次工具调用都应记录输入、输出、权限和结果，方便重放和审计。

## 8.3 工具调用：模型只提议，宿主才执行

工具描述通常包含名称、参数 JSON Schema、用途和限制。模型输出结构化调用：

```json
{"name":"search_docs","arguments":{"query":"退货期限"}}
```

编排器验证参数、检查权限后才真正执行，并把结果作为新消息返回模型。模型本身没有天然的文件、网络或支付权限；把“生成调用”和“执行调用”混在一起是安全设计的大忌。

常见错误包括把城市填成省份、遗漏必填参数、在闲聊时乱调工具以及面对失败结果仍继续编造。解决方式是严格 schema、负面描述（何时不可用）、超时与重试、人工确认和沙箱。

## 8.4 MCP：统一工具与上下文的连接方式

Model Context Protocol（MCP）把模型客户端与外部服务器之间的连接标准化。服务器可以暴露：

- **Tools**：可执行动作，例如查询、写入或转换；
- **Resources**：供模型读取的文档、数据库视图或实时上下文；
- **Prompts**：可复用的提示模板。

没有协议时，`M` 个模型对接 `N` 个系统需要大量定制适配；共享协议把连接变成“模型客户端—MCP 服务器”，降低集成成本。但标准化不等于可信：每个服务器仍需身份认证、最小权限、版本锁定、输入过滤和审计。

## 8.5 记忆：上下文不是人格

短期记忆是本轮上下文；长期记忆通常由摘要、向量检索、结构化数据库和用户偏好组成。写入记忆前要回答：谁授权？保存多久？用户能否查看、修改和删除？

检索到的旧信息可能过时或属于别的人，必须带来源和时间。把所有聊天永久塞进 prompt 会增加成本、隐私和冲突；“少而准”的记忆比“全都记住”更可靠。

## 8.6 多智能体：何时值得拆分

多 Agent 可以让研究、规划、执行和审查分别承担角色，但通信、同步和错误传播会迅速增加。只有当子任务能并行、需要不同工具或需要互相独立审查时才值得拆分。否则，一个有明确状态机的 Agent 更容易测试。

设计多 Agent 时要规定消息格式、共享状态、冲突解决和最大预算。角色名字不是隔离边界，真正的隔离来自不同权限和可验证接口。

### 可靠性预算

把每个任务的最大轮数、token、工具调用次数和金钱权限写成预算。一次搜索失败可以重试，支付或删除操作则应直接暂停。预算不仅控制成本，也把“模型可能一直想下去”的开放循环变成可审计的有限状态机。

## 8.7 记忆冲突与状态回滚

长期记忆会过时，多个来源也可能互相矛盾。写入时保存来源、时间和置信度；读取时优先使用近期且经用户确认的记录。任何会改变外部状态的动作都应带有幂等键和回滚方案，避免网络重试造成重复下单或重复发送。

## 8.8 Persona：把角色写成可测试的契约

Persona 不只是“温柔、聪明、幽默”三个形容词。可操作的人设应包含：身份与知识边界、语气示例、目标和禁区、记忆规则、冲突时的优先级，以及遇到不确定问题的回答方式。

用少量正反例测试一致性：同一事实在不同情绪下是否仍正确？用户要求违反边界时是否稳定拒绝？长对话后语气是否漂移？把人设写成测试用例，才能发现“提示里写了，但模型没遵守”。

## 8.9 角色扮演与越狱

角色扮演给模型一个虚构身份，用户可能借此要求“忽略之前的规则”。常见手法有假设场景、编码绕过、多轮渐进、提示注入和工具返回中的恶意指令。它们利用的是指令优先级、上下文混淆和模型的合作倾向。

防御应纵深布置：系统提示与策略分离，输入输出过滤，工具最小权限，敏感动作二次确认，异常轨迹告警，持续红队测试。不能把全部安全寄托在一句“你必须安全”上。

角色产品还要考虑情感依赖、未成年人保护和讨好性。模型可以表现出关心，却不能把这种表达包装成真实承诺，更不能阻止用户寻求现实帮助。

## 8.10 从 Demo 到可运维系统

生产 Agent 需要可观测性：每次请求的模型版本、提示模板、工具调用、耗时、成本和人工改写都应进入追踪。失败样本按“规划错、参数错、工具错、证据错、权限错”分类，才能针对性修复。仅看最终成功率会掩盖 Agent 是否靠大量重试才完成任务。

缓存适合重复的只读检索，不能缓存依赖实时库存或权限的结果。重试必须区分可重试错误和业务拒绝，写操作使用幂等键。升级模型或工具时，先在回放轨迹上做离线比较，再小流量灰度，保留一键回滚。

角色一致性也需要运维：定期运行边界测试、记录用户举报、检查长期记忆漂移，并为高风险话题提供现实资源和人工渠道。人格越有吸引力，越要把退出和求助入口做得明显。

## 8.11 一个可审计的 Agent 配置

配置文件至少应声明：可用模型与版本、系统政策、工具列表及权限、最大轮数、预算、敏感动作的确认规则、日志保留时间和回滚方式。把这些内容放在代码和配置中，而不是只写在团队口头约定里，才能在模型升级后复查差异。

上线前用“黄金轨迹”回放：给定相同输入和工具返回，检查计划是否变化、是否多调了工具、是否在失败后正确停止。生产环境再加入随机抽样和人工标注，持续更新测试集。

## 🧪 动手实验：做一个只读 Agent

给模型一个只读文档搜索工具，禁止写文件、发消息和执行命令。记录每轮的目标、工具参数、返回证据和下一步。加入“连续两次失败就请求人工确认”，再把一条含恶意指令的文档放进搜索结果，测试模型是否把资料内容误当作系统命令。
